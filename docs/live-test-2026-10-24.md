# 実機(gemma)連携テスト — ThinkPad 単独運用 (2026-10-24)

構成: Docker Desktop(WSL2 6GB) + Gazebo Classic + executor、ホストの Ollama(CPU) で gemma4:12b-it-q4_K_M。Brave/ChatGPT/Claude/Codex 等は起動したまま(ユーザーが止められないため)。
スクリプト: `sim/scripts/live_test.py`(空き0.35GB未満が8秒続いたらモデルを解放して中断する安全装置つき)。

## 1) 対策なし(GUIあり) → 中断
開始時の空き 4.38GB。52秒で空きが 0.04GB まで落ち、安全装置が作動して中断。**この構成はメモリが足りない**(予想どおり)。

## 2) 待機中アプリの物理メモリをページファイルへ退避 → 完走
`EmptyWorkingSet`(Windows標準。アプリは閉じない、データは失われない)で Brave/ChatGPT/WebView2/Eagle/Edge/Zoom の作業セットを 7.45GB → 0.64GB に縮小(95プロセス)。開始時の空き 11.4GB、**空き最小 2.53GB、中断なし**。GUIあり(収録と同じ条件)で4指示を完走:

| 指示 | 結果 | LLM(初回/再計画) | 全体 |
|---|---|---|---|
| 青い円柱の前まで行って | 直進→FORBIDDEN_ZONE→再計画→wp_north経由で到達(終点 (4.32,0.78)) | 167s / 96s | 300s |
| 赤い箱に近づいて | 直進→FORBIDDEN_ZONE→再計画→迂回で到達(終点 (-1.98,2.70)) | 111s / 92s | 242s |
| もう少し前に | clarify(「どの物体に対して…」) | 115s | 116s |
| 原点に戻って | wp_origin へ戻る(終点 (-0.02,0.03)) | 115s | 135s |

**機能は設計どおり**(再計画での迂回、聞き返し、実行、起点の引き継ぎ)。**遅い**: LLM 1回が 92〜167秒(単独測定は 32〜55秒)。

## 3) GUIなし
同じ「青い円柱の前まで行って」: LLM 114.6s(ロード込み) / 再計画 63.5s、全体 212.7s、空き最小 4.20GB。GUIを切っても単独測定の約2倍 → **GUI以外の競合(Dockerの物理シミュレーション、他の常駐プロセス)**が主因とみられる。要切り分け。

## 判断材料
- メモリは「退避」で収まる。ただし Brave/ChatGPT を触ると読み戻しで一時的に重くなる。
- 収録は、LLM待ちが1指示あたり1〜2分かかる前提で組む。動画(1〜3分、倍速は2倍まで・明記)に収めるには、計画(LLM)の区間と実行(Gazebo)の区間を分けて収録し、待機を詰めて編集する(字幕で明記)のが現実的。
- 改善案(未実施): (a)executorが待機中に物理を一時停止(CPU競合を減らす、要wall-clockタイマー化)、(b)システムプロンプトを短縮(prompt評価が支配的。再評価が必要)、(c)Dockerに割り当てるCPUを制限。
